# Outside review, 2026-10-31: what held up and what didn't

## Why this

After the [char-pair run](toy-char-pair-results.md) I wanted outside eyes before building on it. This is the start of an AI gauntlet (see HANDOFF, "Working method"), with one agent so far: Codex CLI running gpt-6-astra at xhigh reasoning, with full shell access but told not to touch the repo or the GPUs. It read the docs and code, ran its own CPU checks, and wrote a report. The prompt, its report and its check scripts are in [`review-2026-10-31/`](review-2026-10-31/).

I checked its main points against the code before taking them on. Everything below marked "checked" I (or Claude) confirmed independently.

## The short version

The A + A' result is real. A gets no prose-specific help through the expert bus, A' gets code from A, and the residual stream hands each model over to the other. But calling it a "direction effect" goes further than the evidence. And the "toward" measure was mixing two things together.

## What it found wrong

1. Every translator started the same way (checked). `fused.seed` is 0 in every config, so all translators share one initialisation and one order of training draws. My "3 seeds" are 3 different model sets, not 3 independent training runs. The code-heavy model is also always in the first slot. Swapping the slots in the forward pass gives exactly swapped outputs, so the code itself doesn't favour A, but the shared start could.

2. "Toward" counts two things (checked). Toward = (how far the real partner pulls the model towards the partner's own view) minus (how far a wrong partner pulls it). A wrong partner that wrecks the model pushes it *away* from the partner's view, and that inflates toward. Astra's counterexample: a real partner that moves the model away from the partner's view can still score a big positive toward. So I've split it:
   - Attraction - JS(alone, partner alone) - JS(paired, partner alone). How far the real partner actually moves the model towards the partner's view.
   - Wrong-partner pull - the same with a wrong partner. Negative means the wrong partner pushes it away (damage). Positive means even a wrong partner pulls it towards the partner's general style.
   - Toward = attraction minus wrong-partner pull, exactly.

   A real, partner-specific transfer needs attraction above zero, above the wrong-partner pull, and above the control partner.

3. The leak audit passed NaN (checked). It counted a position as bad when `diff > tol`, which is never true for NaN, so an all-NaN model passed. No saved result had NaN, but it's fixed now (non-finite counts as a fail) with a test.

4. The wrong-partner control isn't a fixed wrong pair. Both directions roll the batch by one at every link, so the documents chain across layers instead of pairing up. A fixed wrong pairing still gives A about 7.7 bits/char on prose through the residual stream, so it doesn't change the headline, but it muddies the exact size of dependence and toward.

5. The prose test set is thin. It's 48 windows of 256 characters from three papers. Drawing a different set of windows moved e0's residual gain from 0.285 to 0.192 bits/char (same direction, different size). And I've been choosing experiments from this same test set, so it's become a development set.

6. A gate of 0.02 doesn't mean the link is shut. The output projection can make up for a small gate. In e0's residual stream the same final gate injects updates about 6 times larger on prose than on code.

7. The where-knowledge ablations show B *relies on* its experts for prose. They don't show that its transferable prose knowledge sits there.

8. Small one: the character view of each prediction drops the pad's probability without renormalising, so the JS numbers aren't quite JS between proper distributions (up to ~3% missing mass at one position).

## What held up

- It reproduced the char-pair numbers from the checkpoints.
- The residual-stream gain passes its own causality checks, including changing text the model hasn't read yet. No leak.
- The pair-unit model copies are byte-for-byte right, and the backbones get no gradients.
- Removing the final link wipes out most of the residual hand-over (e0, A on prose: all links 1.923, final link alone 1.920, final link removed 2.225). So it's the partner's last-layer prediction being passed through, not the experts working together.
- Zeroing the expert-output content on the bus (keeping the tags) removes A''s code gain (2.027 -> 2.115, alone 2.111). The expert content is what's carrying it.

## The split numbers

Re-ran `scripts/toy_partner_shift.py` on all four result sets. Means of 3 seeds, nats per position. "3/3" = attraction's 95% interval above zero in all three seeds.

| B on code, same-domain control | +0.000 | +0.000 (1/3) | -0.000 |
| B on code, fair force 0.05 | +0.057 | +0.023 (3/3) | -0.033 |

| A on prose, expert bus, partner B | +0.0005 | +0.0021 (3/3) | +0.0016 |

| A on prose, residual, partner A' | +0.472 | +0.075 (3/3) | -0.397 |
| A' on code, residual, partner A | +0.418 | +0.077 (3/3) | -0.341 |
| A' on code, expert bus, partner A | +0.055 | +0.021 (3/3) | -0.033 |

What changes:

- B's code transfer is real but about half the size toward said. Attraction is +0.039, the control is zero.
- λ 50 is worse than "no lean". The real partner pushes B *away* from A's view (-0.030). Toward hid that because the wrong partner does the same.
- B on prose is still "different, not better": attraction +0.002 to +0.004 in 3/3, wrong-partner pull about zero, control negative.
- A on prose through the expert bus does move towards its partner a little (+0.002, 3/3, control zero), but a wrong partner moves it almost as much. So A drifts towards a prose model's general view whichever document the partner reads. That's a partner effect, not prose knowledge, and it's why toward was about zero.
- The residual hand-over is real (attraction +0.075, closing about three-quarters of the gap between A and A''s predictions), but 84% of the old toward number was a wrong partner wrecking the model.

## What I'm taking from it

- The "direction effect" is a pattern in these runs, not a law. It needs independent translator seeds and swapped slots before I lean on it.
- Report attraction, wrong-partner pull and toward together from now on.
- The residual hand-over is a "different because of the partner" model in the plain sense, but it's a hand-over of the final prediction, not experts cooperating. If I want cooperation, I need a test that blocks the final-layer shortcut.
- Fair forcing at 0.01-0.02 can wait.

## Next, by size (see HANDOFF, "the size ladder")

All toy level unless marked. Rough GPU costs are at the char-pair timings (~9 min per translator per card, plus audit).

1. Controls. A new translator seed, swapped slots, A_i with A'_(i+1) (different init), A_i with A_(i+1) as its control, and A'+A' for the reverse direction. About 6-12 translators, 1.5-3 GPU-hours. Needs a slot-swap option and per-unit `fused.seed` in the sweep.
2. What blocks prose. Router-weighted MoE sum instead of the per-expert bus, residual stream without the final link, and a non-zero gate start for A. About 4-8 translators.
3. A 50/50-mix char reader. The models already exist (`results/toy_sweep/s0-s2/model_a.pt`, p_prose 0.5), so no pretraining. About 6 translators.
4. Small level. One bounded pilot on a real small MoE pair, with tests that show a behaviour that follows something specific the partner knows. Days of engineering first.

Also wanted: a second prose test set nobody has looked at, and a fixed wrong-partner pairing in `run_pair`.
